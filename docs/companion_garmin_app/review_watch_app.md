## Verification notes (evidence)

1. **ActivityMonitor permission removal (2ff9ba0) was required, and the fallback is runtime-safe.** Probe compile with `<iq:uses-permission id="ActivityMonitor"/>` re-added fails: `ERROR: Invalid permission provided: ActivityMonitor` (exit 102). `ActivityMonitor` is **not** a permission id in SDK 9.3.0 (permission table in `docs/Core_Topics/Manifest_and_Permissions.html`: Ant, AudioInput, AudioOutput, Background, BluetoothLowEnergy, Communications, ComplicationProvider, ComplicationSubscriber, DataFieldAlert, Fit, PersistedContent, Positioning, Sensor, SensorHistory, SensorLogging, UserProfile). `Toybox.ActivityMonitor` is not permission-gated, so `CadenceSampler.stepDeltaCadence()` calling `ActivityMonitor.getInfo()` cannot hit the fatal "Permission Required" runtime error. The manifest's Communications+Sensor-only permission set is correct and minimal.
2. **Monkey C DOES support try/catch.** `doc/docs/Monkey_C/Exceptions_and_Errors.html`: "Monkey C supports structured exception handling … `try { } catch( ex instanceof AnExceptionClass ) { } catch( ex ) { } finally { }`", and SDK samples use it (`samples/Encryption`, `samples/BackgroundTimer`, …). Probe compile of `try/catch (ex instanceof Lang.Exception)/catch (ex)/finally` for fr245: BUILD SUCCESSFUL. The old code failed because of the invalid catch syntax `catch (ex as Lang.Exception)` — probe compile: `no viable alternative at input '… catch (ex as'`. So commit 47f1ad3's "remove try/catch (not supported)" rationale is factually wrong (the *replacement* pattern is right — see finding 2).
3. **ViewLoop is API 3.4.0 and the fallback is real.** `doc/Toybox/WatchUi/ViewLoop.html`: "Since: API Level 3.4.0" (same for `ViewLoopFactory`, `ViewLoopDelegate`). Device data: fr245 = `connectIQVersion 3.3.1`; all 14 other targets are 5.2.0/6.0.0. The code compiles for fr245 because monkeyc compiles against the SDK API, and the `WatchUi has :ViewLoop` runtime check handles the older device — exactly the pattern of Garmin's own `samples/Primates` (`if (WatchUi has :ViewLoop) { … new WatchUi.ViewLoop(factory, {:page => 0, :wrap => true, :color => Graphics.COLOR_GREEN}) … } else { fallback }`). RunBeat's structure, options dictionary, factory (`getView`/`getSize`), per-page `BehaviorDelegate`s and root `ViewLoopDelegate` (`onNextView`/`onPreviousView` → `changeView(DIRECTION_NEXT/PREVIOUS)`, matching the documented "down button / SWIPE_UP = next page" semantics) are identical to the sample.
4. **Tap-to-activate is NOT a regression.** `BehaviorDelegate` has no `onTap`, but `BehaviorDelegate.onSelect()` is documented as "typically triggered by the Start/Enter button (KEY_ENTER) **or by a CLICK_TYPE_TAP ClickEvent on a touch screen**" — and `RunBeatPageDelegate.onSelect()` calls `_view.onSelectPressed()`. The M8 fix's intent (tap = page's primary action) survives the ViewLoop migration on touch devices (Venu 3, fenix 7/8, epix 2). The Primates sample relies on the same behavior ("Tapping a page will push a new view").
5. **Communications API usage matches `samples/Comm` exactly.** `registerForPhoneAppMessages(method(:onPhoneMessage))` with `onPhoneMessage(msg as Communications.PhoneAppMessage)` reading `msg.data` (Comm sample: identical); `Communications.transmit(json, null, listener)` — the 2nd parameter is an options Dictionary ("for future proofing, an empty Dictionary is used"), not an app id; `ConnectionListener.onComplete()/onError()` (Comm sample `CommListener`: identical). API levels: `transmit` 1.0.0, `Message.data` 1.3.0, `PhoneAppMessage` 1.4.0, `ConnectionListener` 1.0.0 — all ≤ fr245's CIQ 3.3.1.
6. **Fallback-path API levels all ≤ 3.3.1:** `WatchUi.loadResource` 1.0.0, `Dc.setColor(fg, bg)` 1.0.0, `Dc.getTextWidthInPixels` 1.0.0, `Sensor.Info`/`Sensor.Info.cadence` 1.0.0, `ActivityMonitor.getInfo()` 1.0.0, `Timer.Timer` 1.0.0. Resource menus (`Rez.Menus.*`) and `MenuInputDelegate.onMenuItem(item as Symbol)` predate 3.3.1. `minSdkVersion = 3.2.0` in monkey.jungle is consistent (lowest target fr245 = 3.3.1).
7. **`Sensor.getInfo()` without `setEnabledSensors` is doc- and sample-consistent.** `Sensor.getInfo()`: "useful for retrieving the current sensor info either on demand or periodically within a Timer" (1 Hz accelerometer example, no enable call); `samples/AccelMag` reads `Sensor.getInfo()` (accel + mag) on a 100 ms timer with **only** the Sensor permission and no `setEnabledSensors`. `Sensor.Info.cadence`: "derived from … Watch-based cadence calculations" with no enable prerequisite. Residual risk → finding 4.
8. **Build reproduced:** `compile_repo_all.sh` (monkeybrains, SDK 9.3.0, developer key, local device data) on a byte-identical copy of the tree: 15/15 `EXIT=0 PRG=yes` (fr245, fr255, fr265, fr955, fr965, fenix7, fenix7s, fenix7x, fenix8solar47mm, fenix8solar51mm, fenix843mm, fenix847mm, epix2, venu3, venu3s), no warnings in any log.

## Protocol cross-check (watch ↔ phone, field-for-field)

Watch sends (`MessageHandler.mc`) → codec (`GarminMessageCodec.kt`) → router (`GarminCommandRouter.kt`):

| Watch command (MessageHandler.mc) | Codec type | Router action |
|---|---|---|
| `{"type":"toggle"}` (MainView select/tap, fallback select) | `Toggle` | active → `togglePlayPause()`, else media key |
| `{"type":"next"}` / `{"type":"prev"}` (MainViewMenu) | `Next` / `Prev` | active → `playNext()`/`playPrevious()`, else media key |
| `{"type":"cadence_delta","delta":1/-1}` (CadenceViewMenu ±1) | `CadenceDelta(Int)` | `increment/decrementTargetCadence()` (clamped 150–195) |
| `{"type":"cadence_use_current","cadence":172}` (mean, `"%.0f"`) | `CadenceUseCurrent(Float)` | `setTargetCadence()` (non-finite guard + clamp) |
| `{"type":"speed_correction_toggle"}` (ControlView select/menu) | `SpeedCorrectionToggle` | `toggleSpeedCorrection()` |
| `{"type":"volume_delta","delta":1/-1}` (ControlViewMenu) | `VolumeDelta(Int)` | `adjustStreamVolume(STREAM_MUSIC, delta)` |
| `{"type":"mark_not_for_running"}` (ControlViewMenu) | `MarkNotForRunning` | `markTrackNotForRunning()` + `playNext()` + ack |

Phone pushes → watch reads: `state` fields `source, isPlaying, trackId, title, bpm, targetCadence, speedCorrection, playbackSpeed, volume` — all nine are read by `MessageHandler.applyState()` (MessageHandler.mc:100-140) with identical spelling; null/omitted fields tolerated (`optionalFloat`, instanceof checks). `ack` `{command, ok}` — the phone acks exactly the five state-changing RunBeat commands (`GarminCompanionManager.needsAck()`: cadence_set, cadence_delta, cadence_use_current, speed_correction_toggle, mark_not_for_running); `applyAck()` handles all five plus a generic fallback. Transport/volume commands get no ack by design — the watch never blocks on acks (confirmations are transient; the pushed state is the feedback), so no watch UI breakage. Integer-vs-float: the watch formats cadence as a whole number (`"%.0f"`), which parses correctly whether the phone reads Int or Double; `bpm`/`targetCadence` are written by the codec as Int when whole, Double otherwise — the watch's `optionalFloat` accepts both Monkey C `Number` and `Float`. UTF-8 titles: org.json emits printable non-ASCII raw; the watch parser passes raw bytes through and only drops `\uXXXX` escapes (control characters — not present in media titles). UUID: identical in `garmin-watch/manifest.xml:9` and `GarminCompanionManager.IQ_APP_ID`.

## Findings

### 1. [minor] Stale track title on the main page when RunBeat is not active
- **Files:** `garmin-watch/source/MessageHandler.mc:116-118` (title only overwritten when present), `garmin-watch/source/MessageHandler.mc:129-137` (the "clear RunBeat-only fields" block clears `trackId/bpm/targetCadence/speedCorrection/playbackSpeed` but **not** `title`), `garmin-watch/source/view/MainView.mc:43` (shows `_state.title` whenever non-empty, regardless of source).
- **What:** the phone deliberately omits `title` when RunBeat is inactive (`GarminCommandRouter.kt:131-137` — the comment states the goal: "the watch does not show a stale RunBeat title with source `none`"). The watch treats a missing field as "keep the old value", so after RunBeat stops (or an external app takes over), the main page shows the previous RunBeat track title under "Nothing playing"/"External app". Same root cause when the active track simply has no title.
- **Why it matters:** cosmetic but user-visible, and it defeats the stated intent of the phone-side title-omission fix; `title` is the one RunBeat-only field not cleared by the block that clears all the others.
- **Fix:** add `s.title = "";` to the `if (s.source != "RunBeat")` block in `applyState()` (MessageHandler.mc:129-137).

### 2. [minor] Misleading comment: "Monkey C has no try/catch" (and a false commit rationale)
- **Files:** `garmin-watch/source/MessageHandler.mc:174` (`// transmit() reports failure through the ConnectionListener's onError() (Monkey C has no try/catch).`); commit `47f1ad3` message ("remove try/catch (not supported)"); the removed guards were in `CadenceSampler.mc` (`Sensor.getInfo()` / `Sensor.setEnabledSensors()`).
- **What:** try/catch **is** supported in Monkey C (SDK 9.3.0 doc `Exceptions_and_Errors.html`; samples use it; a probe with `catch (ex instanceof Lang.Exception)` compiles for fr245). What actually broke the old code was the invalid catch syntax `catch (ex as Lang.Exception)` (verified compile error). The replacement — `transmit(json, null, ConnectionListener)` with `onError()` — is the officially recommended pattern (`samples/Comm`), so the shipped code is fine; the comment and commit message misstate the language and will mislead maintainers into avoiding legitimate guards.
- **Why it matters:** future readers will wrongly believe they cannot guard sensor/communications calls; the dropped `try/catch` guards around the 1 Hz sensor reads were free insurance against device-specific throws (an uncaught exception in Monkey C terminates the app).
- **Fix:** correct the comment in `MessageHandler.mc:174` (e.g. "transmit() reports failure through the ConnectionListener's onError() callback") and amend the commit message; optionally restore guards in `CadenceSampler.sensorCadence()`/`stepDeltaCadence()` using the correct `catch (ex instanceof Lang.Exception)` syntax.

### 3. [minor] `watch_app_plan.md` contradicts the shipped watch app
- **Files:** `docs/companion_garmin_app/watch_app_plan.md:36` (permissions table lists `ActivityMonitor` — not declared, and not a valid permission id in SDK 9.3.0), `:91` (cites `Communications.transmitAckMessage()` — no such API; the real API is `Communications.transmit(content, options, listener)`; also cites `ConnectIQ.registerForAppEvents()`, which the app does not use), `:98-103` (instructs `Sensor.setEnabledSensors([Sensor.SENSOR_ACCELEROMETER])` with onShow/onHide power management — the shipped `CadenceSampler.mc` does neither, by design), `:125-126` ("Send an ack expectation only for `mark_not_for_running` and `cadence_use_current`" — the phone acks five command types, `GarminCompanionManager.needsAck()`), `:84-86` (interaction model: "navigable with up/down" — no mention of ViewLoop, swipe paging, tap=select, or the fr245 CIQ 3.3.1 MainView-only fallback), `:131` ("All support `ActivityMonitor` live cadence").
- **What:** the plan document still describes the pre-compile-fix design (and an API that never existed).
- **Why it matters:** the docs are the spec the implementation is judged against; a maintainer following watch_app_plan.md would re-introduce a manifest permission that no longer compiles and sensor-enable code that was deliberately removed.
- **Fix:** update the permissions table (drop ActivityMonitor), the cadence-sampling section (no enable call; step-delta fallback needs no permission), the Communications API names, the ack list, and the interaction model (ViewLoop + fallback + tap); or mark those sections as superseded by the shipped code.

### 4. [minor] `Sensor.Info.cadence` without `setEnabledSensors`: doc-consistent but not guaranteed — verify on a real device
- **Files:** `garmin-watch/source/CadenceSampler.mc:82-96` (`sensorCadence()` reads `Sensor.getInfo().cadence` with no enable call), `:70-80` (`readCadence` falls back when cadence is null), `:99-115` (step-delta fallback).
- **What:** the compile fix removed `Sensor.setEnabledSensors([Sensor.SENSOR_ACCELEROMETER])` + onShow/onHide power management, claiming the onboard accelerometer needs no enable call. This is consistent with the SDK docs (`getInfo()` is on-demand; AccelMag sample reads `getInfo()` on a timer with only the Sensor permission) and `Sensor.Info.cadence` lists "Watch-based cadence calculations" with no enable prerequisite. However, the `accel` field note says "Some devices do not enable the accelerometer at startup. To get valid data from this field on such devices, applications must enable the sensor with a call to `registerSensorDataListener`" — if watch-based cadence similarly requires a powered accelerometer on some devices, `cadence` returns null and the app **silently** falls back to the coarse step-delta source (quantized to multiples of 60 spm), so "use current cadence" would set a wrong target (e.g. 180 instead of 172). No crash: `ActivityMonitor` needs no permission (verification note 1).
- **Why it matters:** the primary user story of the cadence page ("average cadence of the last 60 s as target") depends on this source; the degradation is silent.
- **Fix:** verify cadence accuracy on a real device (the plan already schedules this: `implementation_plan.md` Phase 3 "verify cadence accuracy"; add a fr245 + a fenix/Venu). If `cadence` is null while running, re-add sensor enabling (via `setEnabledSensors` or `registerSensorDataListener`) or surface "no cadence source" instead of silently using step-delta.

### 5. [nit] Stale comment in `monkey.jungle`
- **File:** `garmin-watch/monkey.jungle:15-16` — "all targets support >= 3.2 (ActivityMonitor live cadence, SwitchableView, resource menus)".
- **What:** SwitchableView is gone (ViewLoop since 3.4.0 with a runtime fallback), ActivityMonitor is not a permission. `minSdkVersion = 3.2.0` itself is fine (lowest target fr245 = CIQ 3.3.1; all fallback-path APIs ≤ 3.3.1).
- **Fix:** reword the comment (e.g. "all targets ≥ 3.2; ViewLoop paging needs 3.4.0, guarded at runtime with a MainView-only fallback for fr245 @ 3.3.1").

### 6. [nit] Unused imports and dead code
- **Files:** `import Toybox.Lang;` in all 9 source files (`RunBeatCompanionApp.mc:4`, `MessageHandler.mc:2`, `WatchState.mc:1`, `CadenceRingBuffer.mc:5`, `CadenceSampler.mc:2`, `view/BaseView.mc:2`, `view/MainView.mc:2`, `view/CadenceView.mc:2`, `view/ControlView.mc:2`) — no `Lang.*` reference in any file; `CadenceRingBuffer.size()` (`CadenceRingBuffer.mc:64`) and `reset()` (`:68`) are never called.
- **What/why:** harmless (compiles clean, no warnings; Garmin samples also import Lang liberally), but it is migration noise.
- **Fix:** drop the unused imports; keep or remove `size()`/`reset()` deliberately (they are reasonable small API surface for a data structure — removing is optional).

### 7. [nit] `architecture.md` component table omits `GarminCommandRouter` (and `GarminWatchConnection`)
- **Files:** `docs/companion_garmin_app/architecture.md:73` (the `GarminCompanionManager` row says it receives watch messages and "**route** them"), the phone-side components table (lines ~60-80) has no `GarminCommandRouter` row; the routing diagram (lines ~30-40) attributes the routing decision to the manager.
- **What:** the routing table actually lives in `GarminCommandRouter.kt` (the manager is the thin SDK shell that decodes and delegates). `GarminWatchConnection` (the `StateFlow` holder, `GarminConnectionState.kt:29`) is also unlisted.
- **Fix:** add a `GarminCommandRouter` row ("decides RunBeat vs media-key routing, builds state/ack") and adjust the manager row/diagram wording.

### 8. [nit] No automated tests for the watch app
- **Files:** `garmin-watch/` has no test sources (the phone side has `GarminMessageCodecTest`, `GarminCommandRouterTest`, `MediaKeyDispatcherTest`, `CadenceAveragerTest`).
- **What:** Monkey C supports on-device unit tests (`Toybox.Test`), and the hand-rolled JSON parser (`MessageHandler.parseFlatObject`), the ring-buffer math, and the command builders are pure logic that would be cheap to lock down. `watch_app_plan.md` "Testing" currently relies on the simulator + real device.
- **Fix:** add a small `Toybox.Test` suite (parser edge cases: malformed JSON, escapes, nested values, missing fields; ring-buffer window/zero handling; command JSON shapes) and run it in the simulator per device.

### 9. [nit] Launcher icon resolution
- **Files:** `garmin-watch/resources/drawables/launcher_icon.png` (48×48 RGBA); device icon sizes in the local device data: 40×40 (fr245/fenix7/fr955), 60×60 (epix2/fenix8), 70×70 (venu3).
- **What:** the manifest v3 doc says the resource compiler auto-sizes `launcherIcon` to the product icon size — downscaling 48→40 is fine, but upscaling 48→60/70 will look soft on epix 2 / fenix 8 / Venu 3.
- **Fix:** ship a larger source PNG (≥ 70×70, ideally per-size drawables) or accept the mild blur for a sideloaded personal app.
